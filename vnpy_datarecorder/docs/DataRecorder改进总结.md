# DataRecorder改进总结

## 概述

本次改进主要涉及DataRecorder模块的多周期K线录制功能、合成逻辑优化、日志改进以及与HKFEBarGenerator的集成。所有改进已完成并通过测试。

## 一、多周期K线录制功能

### 1.1 功能特性

DataRecorder现在支持录制多个周期的K线数据：
- **1分钟**（`Interval.MINUTE`）：基础周期，从Tick数据合成
- **5分钟**（`Interval.MINUTE_5`）：从1分钟K线合成
- **1小时**（`Interval.HOUR`）：从1分钟K线合成
- **4小时**（`Interval.HOUR_4`）：从1分钟K线合成

### 1.2 UI改进

- 将单一的K线添加按钮改为多选复选框
- 支持同时选择多个周期进行录制
- 显示已录制合约的所有周期信息
- 添加状态反馈标签，显示操作结果

### 1.3 配置存储

- 每个合约的录制配置包含周期列表（`intervals`）
- 自动保存配置到本地JSON文件
- 支持向后兼容（旧配置自动转换为新格式）

## 二、合成逻辑重构

### 2.1 核心改进

**之前的实现：**
- 使用BarGenerator在最后一个1分钟K线完成时合成大周期K线
- 开盘价需要后续修正

**现在的实现：**
- 在新周期开始的第一根1分钟K线时，检测并合成上一个周期
- 直接从数据库加载完整的1分钟K线数据
- 使用第一根1分钟K线的开盘价作为大周期K线的开盘价

### 2.2 关键方法

#### `_aggregate_period_bar()`
从数据库或缓存中加载指定周期内的1分钟K线，使用与DataManager相同的逻辑合成大周期K线。

**特点：**
- 支持从数据库加载历史数据
- 支持从本地缓存获取数据（作为备用）
- 使用第一根1分钟K线的开盘价
- 支持5分钟、1小时、4小时周期

#### `_check_and_aggregate_previous_period()`
检测是否是新周期的开始，如果是则合成上一个周期。

**逻辑：**
- 使用`get_period_start`和`get_hkfe_4hour_period`判断周期边界
- 维护`last_periods`字典记录上一个周期
- 当检测到周期切换时，触发合成

### 2.3 数据流程

```
1. Tick数据到达
   ↓
2. 更新1分钟BarGenerator
   ↓
3. 1分钟K线完成，触发on_minute_bar回调
   ↓
4. 缓存1分钟K线到minute_bars_cache
   ↓
5. 调用_check_and_aggregate_previous_period()
   ↓
6. 检测是否是新周期的开始
   ├─ 是 → 从数据库/缓存加载上一个周期的1分钟K线
   │       ↓
   │      使用第一根1分钟K线的开盘价合成大周期K线
   │       ↓
   │      记录合成的大周期K线
   └─ 否 → 继续
   ↓
7. 记录1分钟K线
   ↓
8. 每10秒批量保存到数据库
```

### 2.4 与DataManager的一致性

**开盘价获取：**
- ✅ 都使用第一根1分钟K线的开盘价
- ✅ 都从数据库加载1分钟K线数据

**周期判断：**
- ✅ 都使用`get_period_start`（5分钟、1小时）
- ✅ 都使用`get_hkfe_4hour_period`（4小时，HKFE交易所）

**合成逻辑：**
- ✅ 都按周期分组1分钟K线
- ✅ 都使用第一根和最后一根1分钟K线的开盘价和收盘价
- ✅ 都计算最高价、最低价、成交量等

## 三、HKFEBarGenerator集成

### 3.1 复用策略

**已复用：**
- ✅ 使用`create_bar_generator`工厂函数创建1分钟K线生成器
  - 对于HKFE交易所，自动使用`HKFEBarGenerator`
  - 对于其他交易所，自动使用标准`BarGenerator`
  - 保持代码一致性和统一的设计模式

**未复用：**
- ❌ HKFEBarGenerator的大周期实时合成逻辑
  - 原因：合成时机不符合需求（实时合成 vs 新周期开始时合成）
  - DataRecorder需要从数据库加载完整数据，确保开盘价正确

### 3.2 实现代码

```python
from vnpy.trader.hkfe_bar_generator import create_bar_generator

bg = create_bar_generator(
    on_minute_bar,
    window=0,
    on_window_bar=None,
    interval=Interval.MINUTE,
    exchange=exchange,
    symbol=symbol
)
```

## 四、日志改进

### 4.1 启动日志

启动时显示：
- 数据录制已启动
- 保存间隔（默认10秒）
- 当前录制任务数量（K线和Tick）
- 已录制的合约列表

### 4.2 定时保存检查日志

每100秒记录一次数据统计：
- 无数据时：`⏰ 定时保存检查：无数据需要保存 (bars: 0, ticks: 0)`
- 有数据时：`⏰ 定时保存检查：准备保存 (bars: X, ticks: Y)`

### 4.3 数据收集日志

- **Tick接收**：每收到100个tick记录一次
- **K线收集**：每收集10根K线记录一次
- **订阅确认**：合约订阅时记录
- **数据过滤**：tick被过滤时记录（每100个记录一次）

### 4.4 保存结果日志

- 成功保存：显示保存的数据量和周期信息
- 保存失败：显示错误信息
- 异常处理：记录详细的异常堆栈信息

## 五、保存机制说明

### 5.1 保存时机

- `process_timer_event`每1秒被调用一次
- 只有当`timer_count >= 10`时才会执行保存（即每10秒执行一次）
- **重要**：只有当`self.bars`或`self.ticks`中有数据时才会真正保存
- 如果两者都为空，不会执行任何保存操作

### 5.2 数据收集

- **K线数据**：通过`record_bar()`方法收集到`self.bars`字典
- **Tick数据**：通过`record_tick()`方法收集到`self.ticks`字典
- 数据按合约和周期分组存储

### 5.3 批量保存

- 每10秒将所有收集的数据放入队列
- 后台线程从队列取出数据并保存到数据库
- 保存后清空已保存的数据（`self.bars.clear()`和`self.ticks.clear()`）

- `_correct_bar_open_price()`：修正开盘价方法（已废弃）

### 6.2 新增的数据结构

- `self.last_periods`：上一个周期记录（用于检测周期切换）

## 九、注意事项

### 9.1 数据依赖

- 合成大周期K线需要从数据库加载1分钟K线数据
- 确保1分钟K线已经保存到数据库
- 数据库查询可能有延迟，缓存机制提供备用方案

### 9.2 内存管理

- 1分钟K线缓存限制为最近60根（约1小时）
- 避免长时间运行导致内存占用过大

### 9.3 性能考虑

- 每100秒记录一次定时检查日志，避免日志过多
- Tick和K线收集日志也采用采样方式，避免过于频繁
