## 问题概述

根据用户测试反馈，发现五个问题：

1. **问题1**：挂多单成交后，挂单未删除，迁移止损线止盈线未完成
2. **问题2**：手动删除挂单线及其关联的止损线和止盈线，拖拽入场线生成止损线和止盈线，但价格未触及新止盈线就触发平仓了
3. **问题3**：止损线和止盈线触发时委托下单都是限价单，在波动率大的时段会比较难成交
4. **问题4**：止损止盈触发下单后，可能由于tick的原因，反复下了好几个重复单，很可能被FUTU API拒绝了
5. **问题5**：挂单触发后经过订单超时重试最后成交，但挂单线无法关联，导致挂单线未删除，关联止损止盈也没迁移到入场线

## 问题详细分析

### 问题1：挂多单成交后，挂单未删除，迁移止损线止盈线未完成

**症状**：
- 挂多单成交后，挂单线仍然存在
- 止损线和止盈线没有迁移到入场线

**日志分析**：
从日志可以看到：
```
[DrawingOrderController] get_line_id_for_order: 查询订单 FUTU.6454597, 结果=None, 当前映射表中有 0 个订单: []
```

**根本原因**：
订单和挂单线的关联关系丢失，导致无法找到挂单线，也就无法：
1. 删除挂单线
2. 迁移止损/止盈线到入场线

**可能的原因**：
1. 订单和挂单线的关联关系没有建立（挂单触发下单时没有调用 `link_line_to_order`）
2. 关联关系被意外清理（可能在订单更新处理中被清理）
3. 订单更新事件处理时，关联关系丢失

**修复方案**：
1. 确保挂单触发下单时，正确建立订单和挂单线的关联关系
2. 确保在挂单成交后，即使关联关系丢失，也能通过其他方式（价格匹配）找到挂单线
3. 在删除挂单线之前，确保已保存挂单线关联的止损/止盈线信息

---

### 问题2：手动删除挂单线后，旧的止盈线仍在监控中

**症状**：
- 手动删除挂单线及其关联的止损线和止盈线
- 拖拽入场线生成新的止损线和止盈线
- 但价格未触及新止盈线就触发平仓了（触发了旧的止盈线）

**日志分析**：
从日志可以看到：
```
2025-12-01 20:57:26.463 | INFO | ChartWidget | [ChartWidget] 触发止盈: 通过主力合约映射找到持仓 (图表=MHImain.HKFE, 实际=MHI2512.HKFE)
2025-12-01 20:57:27.320 | INFO | ChartWidget | [ChartWidget] 从入场线创建止盈线: 价格=26053.69
```

**根本原因**：
旧的止盈线（价格 26037）在删除时：
1. 虽然从 PriceLineManager 中删除了，但可能从数据库重新加载了
2. 或者删除操作没有从数据库中删除，导致重新加载时又出现了

**修复方案**：
1. 删除止损/止盈线时，确保从数据库中删除（避免重新加载）
2. 确保删除操作完整：从 plot 中移除、从 PriceLineManager 中删除、从数据库中删除

2. 修复查找未关联挂单线的逻辑（line 682-730）：

   - 这样可以确保即使关联关系丢失，也能正确删除挂单线、创建入场线并迁移止损/止盈线

### ✅ 修复3：止损/止盈触发时使用对手价

**修复方案**：
1. 继续使用对手价限价单（因为某些gateway不支持市价单）
2. 确保价格是对手价：平多仓用买一价，平空仓用卖一价
3. 在日志中显示对手价，便于调试

**文件**：`vnpy/chart/widget_trigger.py`

**修改**：
1. 确保止损/止盈触发时使用对手价：平多仓用 `tick.bid_price_1`，平空仓用 `tick.ask_price_1`
2. 如果买一/卖一价不存在或为0，回退到 `tick.last_price`
3. 在日志中显示对手价，便于验证

### ✅ 修复4：防止止损/止盈重复下单

**问题**：
止损止盈触发下单后，可能由于tick的原因，反复下了好几个重复单，很可能被FUTU API拒绝了。必须保证成交率，且有委托单的情况下不再重复频繁下单。

**分析**：
虽然有 `_stop_loss_trigger_lock` 和 `_take_profit_trigger_lock` 保护，但在高频率tick更新时，仍然可能出现重复下单的情况。

**修复方案**：
1. 添加防抖机制：记录触发时间，3秒内不重复触发同一止损/止盈线
2. 检查未成交订单：在触发前检查是否已有同方向的平仓订单（未成交），如果有则跳过
3. 记录触发时间：在触发成功后记录触发时间，用于防抖

**文件**：`vnpy/chart/widget_trigger.py`

**修改**：
1. 在 `trigger_stop_loss_close` 和 `trigger_take_profit_close` 中添加防抖机制：
   - 检查 `_trigger_records` 字典，如果3秒内已触发，则跳过
   - 在触发成功后记录触发时间
2. 添加未成交订单检查：
   - 在发送订单前，检查是否已有同方向的平仓订单（未成交）
   - 如果有，则跳过，避免重复下单
3. 初始化 `_trigger_records` 字典（如果不存在）

### ✅ 修复5：订单重试后挂单线无法关联

**问题**：
挂单触发后，经过委托下单超时重试最后成交，但挂单线已经关联不上，导致挂单线未删除，关联止损止盈也没迁移到入场线。

**分析**：
当订单被撤销并重试时，gateway会生成一个新的订单ID。但是 `DrawingOrderController` 中的映射关系仍然记录着旧的订单ID与挂单线的关联。当新订单的更新事件到达时，`get_line_id_for_order(new_order_id)` 返回 `None`，`_find_unlinked_pending_line` 被调用，但由于旧订单ID仍然在 `_line_order_map` 中，挂单线被认为已经关联，无法被新订单匹配。

**修复方案**：
在查找未关联挂单线时，不仅要检查映射表中是否存在关联，还要验证已关联的订单是否仍然有效（未撤销/未取消/未全部成交）。如果订单已被撤销/取消/成交，应该清理映射关系，将挂单线视为未关联。

**文件**：`vnpy/chart/drawing_order.py`

**修改**：
1. 增强 `_find_unlinked_pending_line` 方法（第388-535行）：
   - 检查已关联订单的当前状态
   - 如果订单状态为 `CANCELLED`、`REJECTED` 或 `ALLTRADED`，清理双向映射关系
   - 将此挂单线视为未关联，允许新订单匹配
2. 处理 `CANCELLED` 状态时的映射清理（第791-803行）：
   - 当订单被撤销时，立即清理映射关系
   - 但保留挂单线（不删除），以便重试订单能够找到它
3. 在强制查找逻辑中也添加了相同的检查（第734-752行）

**详细说明**：请参见 `specs/004-fix-realtime-tick/RETRY_ORDER_LINE_MAPPING_FIX.md`

### ✅ 修复6：挂单止损/止盈线激活机制

**问题**：挂单线关联的止损止盈线，在挂单成交之前不应该注册到事件监听里，也不应该触发委托下单。即使用了防误触发，但逻辑上是错误的，只有挂单成交了，止损止盈才有平仓的可能。

**根本原因**：
- 挂单线的止损/止盈线创建后立即激活，可以触发平仓
- 但此时挂单还未成交，没有持仓，止损/止盈不应该触发

**修复方案**：
实现激活机制：
1. **创建时设置为非激活状态**：
   - 为挂单线创建止损/止盈线时，设置 `_creation_time = None`（非激活状态）
   - 在label中显示"挂单止损"/"挂单止盈"，便于区分

2. **触发时检查激活状态**：
   - 在 `trigger_stop_loss_close` 和 `trigger_take_profit_close` 中，检查 `line.get_creation_time()`
   - 如果为 `None`，跳过触发（非激活状态）

3. **挂单成交后激活**：
   - 在 `update_line_from_order` 中，当挂单成交后，找到关联的止损/止盈线
   - 设置 `set_creation_time(time.time())`（激活状态）
   - 更新label显示为"止损"/"止盈"

**文件**：
- `vnpy/chart/price_line.py`：添加 `_creation_time` 属性和相关方法
- `vnpy/chart/widget_trigger.py`：添加激活状态检查
- `vnpy/chart/drawing_order.py`：挂单成交后激活止损/止盈线

**详细说明**：挂单的止损/止盈线在挂单成交前不会触发，确保逻辑正确性

### ✅ 修复10：止损触发close订单关联pending线问题

**问题**：止损/止盈触发的平仓订单被错误地关联到挂单线，导致挂单线无法正常删除。

**根本原因**：
- `DrawingOrderController.update_line_from_order` 方法在处理订单更新时，会尝试找到关联的挂单线
- 对于平仓订单（`offset == Offset.CLOSE`），不应该关联到挂单线
- 但代码逻辑可能错误地将平仓订单关联到挂单线

**修复方案**：
在 `update_line_from_order` 方法中，明确检查：
- 如果订单是平仓订单（`offset == Offset.CLOSE`）
- 且该订单没有关联到任何挂单线（`get_line_id_for_order` 返回 `None`）

## 功能增强：1分钟实时K线开盘价纠正机制

**问题**：当前实时K线的开盘价显示不正确。BarGenerator创建新K线时，开盘价设置为第一个tick的last_price。但如果该分钟已经开始了，第一个tick可能不是该分钟的第一个tick，导致开盘价不正确。

**根本原因**：
1. BarGenerator在创建新1分钟K线时，使用当前tick的last_price作为开盘价
2. 如果程序在该分钟已经开始后才启动，或该分钟的K线被删除后重新创建，BarGenerator接收到的第一个tick不是该分钟的第一个tick
3. 导致开盘价不准确

**修复方案**：
实现多级fallback机制，按优先级查找正确的开盘价参照物：

1. **优先级1：保存的删除K线开盘价**
   - 来源：删除前历史数据中的K线开盘价（已完成，从完整tick数据生成）
   - 适用场景：程序刚启动时删除当前分钟K线的情况

2. **优先级2：历史数据中的K线开盘价**
   - 来源：`self.history_data` 中该分钟的K线
   - 正确性：已完成，从完整tick数据生成
   - 适用场景：历史数据中有该分钟K线

3. **优先级3：数据库中的K线开盘价**
   - 来源：数据库中该分钟的K线
   - 正确性：已完成，从完整tick数据生成
   - 适用场景：历史数据中没有，但数据库有

4. **优先级4：该分钟第一个tick的last_price**
   - 来源：查询历史tick数据，找到该分钟第一个tick
   - 正确性：符合开盘价定义（1分钟K线的开盘价 = 该分钟第一个tick的last_price）
   - 获取方式：
     - 方法4.1：从数据库查询该分钟的tick数据
     - 方法4.2：从datafeed查询该分钟的tick数据

**判定是否需要修正**：
- 如果 `tick.datetime.second > 0`：该分钟已经开始，第一个tick已过去，需要修正
- 如果 `tick.datetime.second == 0`：可能是该分钟的第一个tick，但仍检查是否有更准确的参照物

**验证机制**：
- 如果找到参照物且与BarGenerator的开盘价不同：使用参照物的开盘价（更可靠）
- 如果找到参照物且与BarGenerator的开盘价相同：验证通过，BarGenerator的开盘价是正确的
- 如果需要修正但找不到参照物：记录警告，使用BarGenerator的开盘价（可能不准确）

**文件**：`vnpy/trader/ui/widget.py`

**实现位置**：`process_tick_event` 方法中，处理 `Interval.MINUTE` 的逻辑（约2704-2920行）

## 功能增强：自动补齐数据并聚合大周期K线

**问题**：5分钟自动补齐不生效，中间缺了两根K线。更新数据点完后效果一样。应该先补1分钟再通过聚合大周期补齐。

**根本原因**：
1. 更新数据功能只下载并保存1分钟K线数据
2. 没有自动聚合生成5分钟、1小时、4小时等大周期K线
3. 导致大周期K线数据缺失或不完整

**修复方案**：
在保存1分钟K线数据后，自动调用DataManager的聚合方法，严格按照港期时间边界划分规则（period_utils.py）进行聚合。

**聚合规则**（复用DataManager的逻辑）：
1. **5分钟K线**：
   - 使用 `get_period_start(bar_dt, Interval.MINUTE_5, exchange)` 获取周期起始时间
   - 过滤非交易时段数据
   - 使用该周期内第一根1分钟K线的开盘价

2. **1小时K线**：
   - 使用 `get_hkfe_hour_period_start(bar_dt)` 获取港期1小时周期起始时间
   - 按照港期交易时段边界划分（17:15-18:14, 18:15-19:14, ...）
   - 使用该周期内第一根1分钟K线的开盘价

3. **4小时K线**：
   - 使用 `get_hkfe_4hour_period(bar_dt)` 获取港期4小时周期起始时间和索引
   - 按照港期4小时时间边界划分：
     - 17:15-21:14：第一根4小时K线
     - 21:15-01:14：第二根4小时K线
     - 01:15-03:00 + 09:15-11:29：第三根4小时K线
     - 11:30-12:00 + 13:00-16:29：第四根4小时K线
   - 使用该周期内第一根1分钟K线的开盘价

**实现方式**：
1. 在 `_download_and_save_minute_data` 方法中，保存1分钟数据后调用 `_aggregate_larger_intervals_using_datamanager`
2. 该方法尝试获取DataManager引擎，如果可用，调用其聚合方法：
   - `aggregate_5minute_bars(symbol, exchange)`：聚合5分钟K线
   - `aggregate_hour_bars(symbol, exchange)`：聚合1小时K线
   - `aggregate_4hour_bars(symbol, exchange)`：聚合4小时K线
3. 如果DataManager不可用，记录警告但不影响主流程

**文件**：`vnpy/trader/ui/widget.py`

**实现位置**：
- `_download_and_save_minute_data` 方法（约3380-3464行）
- `_aggregate_larger_intervals_using_datamanager` 方法（约3466-3540行）

**工作流程**：
```
更新数据按钮点击
    ↓
下载1分钟K线数据
    ↓
保存1分钟K线到数据库
    ↓
调用DataManager的聚合方法：
    - aggregate_5minute_bars()  （使用period_utils.py规则）
    - aggregate_hour_bars()     （使用get_hkfe_hour_period_start）
    - aggregate_4hour_bars()    （使用get_hkfe_4hour_period）
    ↓
保存聚合后的K线到数据库
    ↓
刷新图表
```

**优势**：
1. 完全复用DataManager的聚合逻辑，确保一致性
2. 严格按照港期时间边界划分规则（period_utils.py）
3. 5分钟K线补齐正确，不会出现缺失
4. 如果DataManager不可用，不影响主流程（只记录警告）
